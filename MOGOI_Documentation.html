Introduction

MOGOI is an always-on AI daemon — not a tab-bound chatbot.

MOGOI is designed to keep running in the background, maintain memory over time, watch what is happening across your setup, and act through real tools and connected machines. You can run the daemon locally or on a VPS, keep it alive 24/7, and connect sidecars on other machines so one MOGOI instance can reach your laptop, desktop, and server at the same time.

⚠ Warning — MOGOI can control your desktop, filesystem, applications, browsers, and online accounts. Treat it like giving a trusted human remote access to your machines.
📖 Read these first — Disclaimer & Liability · Authority & Safety

Read This Before You Deploy It

MOGOI is not a toy chatbot. It can be given access to files, terminals, browsers, messaging channels, and remote machines.

Before you expose it over the network, connect real accounts, or raise its autonomy level, review:

  • Disclaimer & Liability
  • Authority & Safety

What Makes MOGOI Different

Most AI products are request/response systems. You open a UI, ask something, and the model disappears until the next prompt.

MOGOI is built around a different operating model:

  • A persistent daemon that keeps state and stays online
  • A web dashboard served directly by the daemon
  • An ambient Pebble mode that lives at your cursor (Windows today; the dashboard is the cross-platform surface)
  • A memory vault backed by SQLite
  • Tool use, browser control, workflow execution, and delegated sub-agents
  • Authority rules that gate risky actions at runtime
  • Sidecars that give MOGOI desktop, browser, terminal, filesystem, and screenshot access on each machine

Platform Support

  • The daemon runs on macOS, Linux, and Windows via WSL2 or Docker. Native Windows is not supported for the daemon.
  • The sidecar runs natively on Windows, macOS, and Linux.
  • Ambient/Pebble mode is Windows-only today; cross-platform ports are planned. The dashboard works everywhere.

High-Level Architecture

At a high level, MOGOI has three layers:

  1. The daemon
  2. The dashboard
  3. Sidecars

Access is JWT-only by default: you enroll each device with mogoi enroll and the sidecar connects with that token, which also unlocks the dashboard. Sidecars are required for the default access path and for any desktop or browser control; you can only skip them by enabling insecure_open_access during setup.

The Daemon

The daemon is the brain. It owns:

  • LLM routing and fallback providers
  • Conversation history and persistent memory
  • The tool execution loop
  • Multi-agent delegation
  • The authority engine and approval system
  • Workflows, goals, awareness, and background services
  • The HTTP and WebSocket server that powers the dashboard

The Dashboard

The dashboard is the control surface. On Windows, the ambient Pebble is the default surface after onboarding, and the dashboard remains available as the full control plane. It exposes the main product areas as rooms:

  • Home · Workflows · Memory · Tools · Agents
  • Authority · Logs · Calendar · Goals · Tasks
  • Content · Workspaces · Usage · Settings

Sidecars

Sidecars are how MOGOI reaches your machines. Each sidecar authenticates to the daemon with a JWT over WebSocket and exposes capabilities from that host, such as: desktop automation, browser automation, terminal access, filesystem access, clipboard, screenshots and awareness capture.

This lets you keep MOGOI running on an always-on server while still giving it hands and eyes on the machines you actually use.

Core Product Areas

The current product centers around these capability groups:

  • Conversational agent with streaming responses and tool use
  • Persistent memory and knowledge extraction
  • Browser and desktop control
  • Voice input and streaming TTS
  • Multi-agent delegation, gated by the authority engine
  • Continuous awareness and proactive suggestions
  • Workflow automation
  • Goal tracking and accountability
  • Web app building and deployment (Workspaces)
  • Multi-provider LLM routing with fallback (Anthropic, OpenAI, Gemini, Ollama, Groq)

Installation

Run MOGOI in Docker, locally via Bun, or on a server.

MOGOI can run in Docker (recommended), on your local machine via Bun, on a home server, or on a VPS.

🔒 Security First — MOGOI can control files, terminals, browsers, remote channels, and connected machines. Treat installation as a security decision, not just a package install. Before exposing the dashboard outside localhost or giving MOGOI access to real accounts, read Disclaimer & Liability and Authority & Safety.

Recommended Install: Docker

Docker runs MOGOI on any OS with a single command. No Bun or other dependencies required.

1. Install Docker Desktop

Download Docker Desktop for Windows, macOS, or Linux if you do not have Docker yet.

2. Run the daemon

Terminal
docker run -d --name mogoi \ -p 1846:1846 \ -v mogoi-data:/data \ ghcr.io/Motius/mogoi:latest

The image is published to GHCR for amd64 and arm64. All daemon state lives in the mogoi-data volume, mounted at /data.

LLM providers, API keys, and model routing are configured from the settings dashboard after first boot. They are stored in the database and encrypted keychain, not in env vars or config.yaml.

Important limitation — The daemon inside Docker cannot access your host desktop, browser, clipboard, or native apps. To give MOGOI desktop awareness and automation on a machine, install the sidecar on that machine. This is a required step, not an optional one.

3. Enroll your first device

Because the daemon runs inside a container, run the enroll command through docker exec:

Terminal
docker exec mogoi mogoi enroll "my-desktop"

This prints an enrollment token. You will paste it into the sidecar in the next step.

Other Installation Options

Option 1: Bun Package

Use this if you want a native local install and already have Bun:

Terminal
bun install -g @motius/brain mogoi start

Option 2: One-Liner Installer

Terminal
curl -fsSL https://raw.githubusercontent.com/Motius/mogoi/main/install.sh | bash mogoi start

Option 3: Manual Repository Install

Terminal
git clone https://github.com/Motius/mogoi.git ~/.mogoi/daemon cd ~/.mogoi/daemon bun install bun run build:ui bun link mogoi start

Requirements

  • Docker, or Bun for a native install
  • A supported OS: Linux, macOS, or Windows via Docker or WSL2
  • An API key for at least one LLM provider (configured in the dashboard after first boot)

Choosing Where to Run the Daemon

Local Machine — Best when you are just getting started, want the simplest setup, or mainly use one machine. Tradeoff: MOGOI only stays online while that machine is on.

VPS or Home Server — Best when you want MOGOI available 24/7, want one daemon to coordinate multiple machines, or care about uptime more than local-only simplicity. Set daemon.brain_domain with an explicit scheme for sidecars to dial the right endpoint.

Quick Start

Get MOGOI running, enrolled, and controlling your machine in minutes.

This guide assumes you have Docker Desktop installed. If you prefer a native Bun install or a source checkout, see Installation, then continue from Step 2.

Step 1: Run the Daemon

Terminal
docker run -d --name mogoi \ -p 1846:1846 \ -v mogoi-data:/data \ ghcr.io/Motius/mogoi:latest

The daemon boots and listens on port 1846. All state lives in the mogoi-data volume.

Step 2: Enroll This Machine

Since 0.9, access is JWT-only by default. You enroll each device from the machine running the brain:

Terminal
docker exec mogoi mogoi enroll "my-desktop"

On a native install, run it directly: mogoi enroll "my-desktop". This mints a long-lived enrollment token and prints it. Keep the terminal open; you paste this token into the sidecar in Step 4.

Step 3: Install and Run the Sidecar

Terminal
bun install -g @motius/sidecar mogoi

The sidecar is the machine-level actuator: desktop automation, browser automation, terminal, filesystem, clipboard, and screenshots. Even a single-machine setup needs it, because the Docker container cannot reach your host desktop.

Step 4: Paste the Enrollment Token

On first run, the sidecar opens a connect window. Click Paste your enrollment token, paste the token from Step 2, and connect. You can also pass it on the command line:

Terminal
mogoi --token <your-token>

The token is stored locally at ~/.mogoi/sidecar.yaml, so subsequent runs reconnect automatically.

Step 5: Finish Setup in the Dashboard

Once the sidecar connects, open the dashboard: http://localhost:1846

On first boot, the dashboard guides you through: Primary LLM provider and API key, Voice (TTS) choice, A conversational profile interview, and a short tour.

Step 6: Send a First Real Task

Good first prompts are tasks that exercise the system, not toy questions. For example:

  • "Summarize what this project actually does."
  • "Open the docs and tell me what is missing."
  • "Create a workflow that posts a Telegram summary every morning."
  • "Plan my day from my current goals."
✅ Quick Verification Checklist — You are in a good state if: the daemon is running (docker ps or mogoi status), the sidecar shows as connected, the dashboard connects successfully, chat messages stream normally, and your selected LLM provider responds.

Configuration

Since 0.9, configuration is split between two homes: the system config and the dashboard settings.

  • ~/.mogoi/config.yaml: system configuration only. The daemon treats it as read-only: daemon, auth, google, browser, timezone, cron.
  • The dashboard settings (stored in the database): everything user-facing. LLM providers and API keys (keys go to an encrypted keychain), voice/TTS/STT, channels, authority, heartbeat, awareness, personality, goals, workflows, sites.

Use MOGOI runs on built-in defaults if the file is absent. Create it by hand (start from config.example.yaml in the repo) when you need to change system settings. A file that exists but fails to parse is a fatal error.

The System Config: config.yaml

config.yaml
daemon: port: 1846 data_dir: "~/.mogoi" db_path: "~/.mogoi/mogoi.db" brain_domain: "https://mogoi.example.com" drain_deadline_ms: 75000 auth: insecure_open_access: false google: client_id: "..." client_secret: "..." browser: local: true timezone: "Europe/Rome"

daemon

Where the daemon listens and stores data. brain_domain matters as soon as anything connects from another machine. listen: "unix:/abs/path.sock" switches to a unix socket instead of TCP.

auth

There is exactly one key: insecure_open_access. Access is JWT-only by default. Setting insecure_open_access: true disables auth entirely for first-time setup; the daemon logs a loud warning the whole time it is on.

browser

local: false stops the daemon from ever launching a local Chromium; browser actions route to a connected sidecar's browser. Recommended for headless servers.

Environment overrides

MOGOI_PORT, MOGOI_HOME, MOGOI_BRAIN_DOMAIN, MOGOI_WAKE_ENGINE, MOGOI_REALTIME_VOICE, MOGOI_TELEMETRY. LLM provider configuration is intentionally not read from env vars.

Dashboard-Managed Settings

Everything else lives in Settings in the dashboard and applies without a restart:

  • LLM: providers, API keys, single-model or multi-tier routing
  • Voice: TTS, STT, wake engine, realtime voice
  • Channels: Telegram
  • Authority: autonomy level, governed categories, overrides
  • Awareness, heartbeat, personality, goals, workflows, sites

Telemetry defaults to on and can be disabled with telemetry.enabled: false, MOGOI_TELEMETRY=0, or DO_NOT_TRACK=1.

Browser Control

MOGOI controls a real browser instance using the Chrome DevTools Protocol (CDP).

MOGOI auto-detects Chrome, Brave, Edge, or Chromium on your system, launches it with a dedicated profile, attaches, and exposes ten browser tools to the agent.

How It Works

The browser launches lazily the first time a browser tool is used, not at daemon startup:

  1. If a browser is already running with a reachable CDP endpoint, MOGOI attaches to it
  2. Otherwise it scans for a supported browser binary and launches it with remote debugging
  3. Pages are snapshotted as a DOM scan of interactive elements, and the agent interacts using numbered element IDs

Browser tools also route to sidecars: every browser tool accepts a target, and when omitted the call auto-routes to a connected browser-capable sidecar.

Supported Browsers

On Linux, MOGOI probes absolute paths in order: Google Chrome, Brave, Microsoft Edge, Chromium. macOS and Windows check the standard install locations. To disable local browser control entirely, set browser.local: false.

The Browser Tools

browser_navigateNavigate to a URL; returns page text plus interactive elements
browser_snapshotRe-scan the current page; returns text plus numbered elements
browser_clickClick an element by element_id from the last snapshot
browser_typeType into an element (element_id required)
browser_hoverHover an element by element_id
browser_press_keySend a key or combination to the page
browser_scrollScroll the page or an element
browser_evaluateExecute JavaScript in the page context
browser_screenshotCapture the page as PNG

The sidecar runs natively on each platform — Windows, macOS, and Linux — using platform-specific APIs for window management, UI automation, screenshots, and input simulation.

Windows

Desktop automation uses native UI Automation COM. PowerShell is used for window enumeration, SendKeys, and screen capture. OCR uses Windows.Media.Ocr. Windows 11 has the required WebView2 runtime preinstalled.

Multi-Agent System

Delegate tasks and manage sub-agents. Authority stays with the top-level agent.

MOGOI features a multi-agent hierarchy with delegation and management tools. An AgentTaskManager coordinates specialist roles. Sub-agents are denied governed actions — authority stays with the top-level agent.

Nine Specialist Roles

  • Personal Assistant — general-purpose everyday productivity
  • CEO Founder — strategic and business decisions
  • Chief of Staff — coordination and follow-through
  • Dev Lead — engineering oversight and code review
  • Executive Assistant — admin and scheduling
  • Marketing Director — campaigns and positioning
  • System Admin — infrastructure and operations
  • Research Specialist — deep research and analysis
  • Activity Observer — monitoring and awareness

Roles are defined in roles/*.yaml. Each role specifies: description, responsibilities, autonomous_actions (free), approval_required (gated), and tools (allow-list). Copy a role to create a custom one.

Sub-Agent Authority

Sub-agents run through the same authority engine with two differences: governed actions are denied outright for sub-agents (they cannot request approval; authority stays with the top-level agent), and a parent can pass a temporary grant for a specific category for the duration of a delegated task.

Memory & Knowledge

The Vault extracts entities, facts, relationships, and commitments from every conversation.

MOGOI's Vault Extractor is an LLM-powered knowledge extraction system that automatically extracts structured knowledge from conversations and stores it in a SQLite knowledge graph.

Features

  • Automatic Extraction — Extracts structured knowledge from unstructured conversations
  • Entity Recognition — Identifies people, projects, tools, places, concepts, and events
  • Fact Extraction — Captures attributes and properties of entities
  • Relationship Mapping — Discovers connections between entities

Relevant knowledge is injected into the system prompt on every turn so MOGOI always remembers what matters. The knowledge graph is stored in SQLite at ~/.mogoi/mogoi.db.

Authority & Safety

Runtime enforcement with soft-gate approvals. Full audit trail.

The authority system controls how much autonomy MOGOI has. It determines which actions the agent can take on its own, which require your approval, and which are blocked entirely.

Authority Levels

Action categoryMinimum levelImpact
read_data1read
spawn_agent1write
write_data3write
send_message3external
execute_command5destructive
access_browser5external
control_app5write
send_email7external
install_software7destructive
make_payment9destructive
delete_data9destructive

default_level (shipped default: 3) is a floor, not a fallback. The dashboard authority slider is that floor.

Approval Workflow

When an action requires approval, MOGOI asks everywhere you are: Dashboard (an approval card with approve/deny buttons) and Telegram (a plain-text message; reply approve <id> or deny <id>).

Emergency Controls

StateEffect
normalAgent operates according to authority rules
pausedAgent still receives messages, but every tool call returns blocked
killedAgent fully stopped. No responses, no actions.

Learning & Auto-Approve

When you approve the same type of action repeatedly, MOGOI suggests an auto-approve rule. A denial resets the counter. This gradually reduces approval fatigue for routine actions.

Audit Trail

Every authority decision is logged to the audit_trail table in the SQLite database. View recent decisions in the Authority room.

Troubleshooting

Known failure points and their fixes.

Daemon won't start

  • Check if the daemon is already running: mogoi status
  • Stale lockfile: remove ~/.mogoi/mogoi.pid
  • Config parse failure: mogoi doctor reports it

Sidecar won't connect

  • Verify the daemon is running: mogoi status
  • Re-enroll: mogoi enroll "device-name" and paste the new token
  • Check firewall — port 1846 must be reachable
  • Set daemon.brain_domain with an explicit scheme

No LLM providers configured

Configure in dashboard Settings → LLM. Any llm: block in config.yaml is ignored; providers are stored in the database + encrypted keychain.

Browser fails to launch on a server

No display available: set browser.local: false and route browser actions through a sidecar on a desktop machine.

Sidecar version too old

Update the sidecar: bun update -g @motius/sidecar or grab a newer binary from GitHub Releases. Local dev builds are never blocked.

Autostart

Start MOGOI automatically on login or boot.

Configure MOGOI to start automatically when you log in or boot your machine.

Linux

MOGOI uses a systemd user service: ~/.config/systemd/user/mogoi.service. Managed via mogoi CLI. Requires loginctl enable-linger on servers.

Terminal
mogoi start -d # enables autostart systemctl --user enable mogoi.service

macOS

MOGOI uses a launchd user agent: ~/Library/LaunchAgents/ai.mogoi.daemon.plist (RunAtLoad, KeepAlive).

Terminal
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/ai.mogoi.daemon.plist

Windows

Native Windows daemon is not supported. Use WSL2 or Docker. The Windows sidecar uses HKCU Run for autostart.

WebSocket API

Real-time communication between the daemon, dashboard, and sidecars.

MOGOI uses a binary WebSocket protocol for real-time communication. The daemon serves WebSocket connections on the same port as the HTTP server.

Endpoints

  • ws://localhost:1846/sidecar/connect — Sidecar enrollment and messaging
  • ws://localhost:1846/ws — Dashboard WebSocket
  • ws://localhost:1846/api/webhooks/* — Webhook endpoints

Authentication

All WebSocket connections require JWT authentication. Sidecars authenticate with enrollment tokens. Dashboard sessions use cookie-based authentication from the panel session.

Protocol

The binary WebSocket protocol carries:

  • Mic audio (WebM) and TTS audio (MP3) on the same connection
  • RPC commands from daemon to sidecar
  • Capability announcements and events
  • Screen capture and OCR data

Public Routes

Only four routes are unauthenticated: /health, /sidecar/connect, the JWKS endpoint (/api/sidecars/.well-known/jwks.json), and /api/webhooks/*.

Contributing

How to modify, extend, and contribute to MOGOI safely.

MOGOI is designed to be reshaped safely. Change behavior through roles and config first, UI and pieces second, core code last.

Safe Change Zones

  • Configuration — ~/.mogoi/config.yaml (traits, authority, cron, TTS/STT, active_role)
  • Roles — roles/*.yaml (description, responsibilities, tools, approval lists)
  • Dashboard UI — edit ui/src/, then bun run build:ui
  • Workflow pieces — src/workflows/mogoi-pieces/, run bun run build:workflows
  • TypeScript behavior — agent loop, tools, daemon services (keep strict, ESM, path aliases)
  • Go sidecar — only via sidecar/Makefile matrix builds

Change Workflow

Terminal
git status && git pull --ff-only # 1. Edit # 2. Rebuild what you touched bun run build:ui # if ui/ changed bun run build:workflows # if workflow framework changed # 3. Verify bun test bun run check:no-ee && bun run check:migrations && bun run lint:templates && bun run check:package mogoi doctor # 4. Restart and watch mogoi restart && mogoi logs -f

Guardrails

  • Pre-commit hooks are mandatory: no-EE check → migration check → template lint → package-files check → bun test --bail (240s timeout)
  • Never vendor ee/ paths (Activepieces Enterprise License)
  • Migrations are expand/contract — never rewrite a shipped migration
  • Keep bun.lock and package.json#files coherent
  • Never ship insecure_open_access: true as a default
  • Never embed secrets in commits
  • Keep versions coherent: package.json, sidecar/VERSION, sidecar/installer/VERSION
💡 Rule of thumb — Reshape behavior through roles and config first, UI and pieces second, core code last. The machine is built to be reshaped — just reshape it in the order it was designed to bend.
